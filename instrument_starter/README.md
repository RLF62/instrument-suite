# New instrument starter — Fischer Instrument Suite

Point the next development session at this README and provide a clear front-panel screenshot. Build and test on the development Pi (`192.168.1.108`). The preview files here are an example, **not an installed controller or an approved catalog entry**. Production Pi `.250` changes only after review, a signed release, and a dry run.

## What to provide for a new instrument

- A straight-on, readable photo or screenshot of the front panel; model and manufacturer as printed on it. Include a rear-panel photo if connectors matter. Confirm you have rights to publish images before adding them to GitHub.
- Connection method (USB-GPIB, Ethernet, serial, etc.), address/IP, and available manuals or command references. Share sample `*IDN?` output if available. Say which controls may change outputs or instrument state.
- Which buttons and displays should work in Classic and Modern, and what stays physical-only. Tell us whether the device can be operated safely while disconnected.
- Desired saved preferences, plot/measurement features, and documentation links. We can start with the screenshot and gather these details as we work.

## Start on `.108`

1. Use the single repo checkout at `/home/pi/release-v1.0.4-sources/suite` (directory name is historical); pull the reviewed `main` branch and check `git status --short`. Avoid editing installed files as the only copy of a change.
2. Preview the no-hardware reference: from repo root run `/home/pi/instrument-suite/venv/bin/python -m unittest test_instrument_starter -q`. To view it locally on the Pi, run `/home/pi/instrument-suite/venv/bin/python -m instrument_starter.app` and open `http://127.0.0.1:8099/classic` via the Pi; stop it with Ctrl+C. It never starts a system service or touches hardware.
3. Create a distinct controller source under `controllers/<tool-id>/`; preserve the original panel image and document any crop/overlay. Keep instrument queries and writes behind a separate hardware layer, with a disconnected/read-only state and explicit control authorization. Do not make startup or page loading change instrument output.
4. Build Classic and Modern pages from `instrument_starter/templates/instrument.html` and `static/starter.css`. Use one `<meta name="viewport" content="width=device-width, initial-scale=1">`; use flexible widths (`minmax(0,1fr)`, `max-width:100%`) for front-panel images, overlays, plots, and controls. Test at Android portrait widths (~360–430 CSS px) and desktop widths; avoid changing desktop geometry while fixing mobile.
5. Register the tool with the **server-rendered** suite header in `suite_navigation.py`: add its ID to `TOOLS` and mappings to `TITLES`, `LABELS`, `VIEWS`, `DOCS`; call `suite_navigation.install(app, current='<tool-id>')` in the controller. The ID must match the reviewed registry/catalog entry. Give each page only **one** top navigation; do not copy a legacy header/nav into the instrument template. The shared header owns Suite Home, installed instrument links, Classic/Modern, docs, and mobile scroll behavior. Keep Customize layout in the shared header actions when implementing its real layout editor, and test placement on Android and desktop.
6. Update `navigation.js` fallback maps and any suite host route/proxy mapping needed for the new tool. Choose a port that is free on all target Pis; add the ID, address, service name, and documentation to the installer, deployment profiles, approved catalog, and signed release component list. `build_release.py`, `maintenance/security.py`, and installation policies currently enumerate the six components explicitly: adding a new tool requires a reviewed change to that schema and its migration, not just copying a directory. Do **not** advertise a tool in Add instruments until its package and installer are tested and signed.
7. Check both directions of every link on `.108`: Classic↔Modern, Suite Home, all installed instruments, Add instruments, docs. Check exactly one visible sticky header on both instrument views. Confirm no console errors and no duplicate header after a direct URL load and after navigating via the buttons. Verify mobile layout and front-panel width on an actual Android Chrome viewport.
8. Run targeted controller tests and suite regression tests (`/home/pi/instrument-suite/venv/bin/python -m unittest discover -q`; use `node --test test_navigation.js` if Node is available). Verify actual HTML, not just a template file. Review the release overlay for both views, make a signed release and dry run on the target Pi before applying. A final clean-install test is useful for major installer/catalog changes.

The shared header is injected by `suite_navigation.install()` into HTML responses. The preview temporarily registers only a display name and view routes in its own process; it does not enroll a real instrument, bind a LAN port, or alter the running suite. The controller must replace that preview registration with the reviewed permanent mappings and service integration above.
